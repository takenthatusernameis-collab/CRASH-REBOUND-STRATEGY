## 3. PERSISTENCE MODEL — corrected 2026-11-21T10:22:00Z (read before trusting any runner)

The previous handoff claimed the `background_process ... persistent=true` runner was "the only durable mechanism". That is **half wrong**, and the wrong half caused a stalled job:

1. **A runner is job-scoped, not machine-scoped.** The controller (`.github/workflows/main.yml`) starts one GitHub Actions job with a **355-minute cutoff** (`timeout-minutes: 360`). Inside that job it runs up to 1000 sequential `kilo` sessions (900 s idle timeout each). A `persistent=true` runner survives session boundaries **inside that job only**. When the job ends, the container is destroyed and the runner dies.
2. **A new job is a fresh container:** fresh checkout, **no `.venv`** (it is gitignored), **no runner**. The first session of every job must therefore bootstrap the venv and resume the runner once. This is normal, not a failure — do not "fix" it, do not treat it as a crash, do not skip the resume.
3. **The real cross-job durability is git.** The controller commits the worktree after each session (`chore(kilo): checkpoint agent session`) and pushes it. The runner's checkpoints live in `research_state/` (`c25_ckpt_*` per completed cell, `c25_draw_ckpts/c25_partial_perm_*_chunkNNNNN.json` every 500 draws) and are committed, so a dead runner costs at most the uncommitted tail of one chunk. Verify with `git log --oneline -5` — if the newest checkpoint commit is old, the previous sessions did not persist and you must resume before anything else.
4. **`schedule_wakeup` is session-scoped and routinely lost** when the 900 s idle watchdog kills the process before it fires. Arm it as a convenience (step 0), never as the source of truth. The controller's sequential sessions are the actual loop: a session that ends is followed by another session with the same prompt.
5. **Do not spin sessions.** If the runner is ALIVE and nothing needs fixing, do **one bounded wait** (§4) and end. Ending instantly in a tight loop burns the model quota and produces the upstream rate-limit failures ("Sign up for free to continue", HTTP 429) that have already killed controller loops in this repository's diagnostics ledger.
